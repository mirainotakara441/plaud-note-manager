## 1. なぜ作るのか

2026-09-12 の総点検で、AIワークOS の現状は
**「入力を整形し、記憶を引き、1回だけ考えて、返す」装置が17本ある状態**だと分かった。
土台（記憶層・自動パイプライン・幻覚対策）は健全で、資産と呼べる実装もある。
足りていないのは機能ではなく、次の3つの構造的欠損である。

| 欠損 | 実態 |
|---|---|
| (a) 起動点が無い | LLMを呼ぶ処理17本すべてが受動。cron 2本はどちらもLLMを呼ばない。「自ら考える」の"自ら"にあたる起動条件がコード上に存在しない |
| (b) 自分で探す手が無い | tool use がリポジトリ全体で未使用。資料取得は `match_count: 40` のような固定の決め打ちで、AIは「この人物の別の接点も見たい」と追加取得できない |
| (c) 結果を知る仕組みが無い | 「今朝の気づき」はDBに残らず毎回その場で計算し直される。採らなかった打ち手も記録されない。**AIは自分の提案が当たったか外れたかを永久に知らない** |

夜間参謀は、このうち **(a) と (c) を同時に埋める最初の1本**である。
(b) は Phase 2 で提案エージェントのツール化として扱う。

### 既存の「毎朝の参謀」との関係

既存の `lib/advisor/` は **LLMを1回も呼ばない完全ルールベース**で、
検知器6本（目標/取り込み/記憶/記録/辞書/誤字）が閾値超過を列挙している。
`lib/advisor/types.ts` に明記された作法は次のとおりで、これは実害から生まれた規律である。

> 事実だけ書く。原因は断定しない。判定できないものは判定しない。
> （2026-08-03の歩数の件は、原因を断定していたら真逆の結論になっていた）

**この規律は一切変えない。** 夜間参謀は既存参謀を置き換えるものではなく、
その隣に**「仮説」という別の層**を足すものとする。両者は画面上でも明確に分ける。

| | 毎朝の参謀（既存） | 夜間参謀（新設） |
|---|---|---|
| 中身 | ルールベース。閾値判定 | LLM。本文を読んで考える |
| 言うこと | 事実（何日空いた・何件溜まった） | 仮説（何が起きていそうか・次に何をすべきか） |
| 断定 | しない | 「仮説」と明示したうえで踏み込む |
| 起動 | ホームを開いた時に計算 | 毎晩の自動実行 |
| 保存 | 残らない（判断だけ `advisor_finding_state`） | `insights` テーブルに本文ごと残る |

## 2. 何をするのか

毎晩1回、その時点の記憶を**領域横断で**読み、翌朝に出す示唆を生成して `insights` に保存する。

現状、領域はきれいに縦割りになっている。健康ルートは健康しか読まず、提案ルートは営業しか読まない。
週次振り返りの下書きだけが日記＋会議＋週報＋健康を横断するが、それも1週分に閉じている。
**「最近の体調の落ち方と商談の失速が同じ週から始まっている」のような気づきを出せる場所が、今どこにも無い。**
夜間参謀はその場所になる。

### 読む材料（すべて既存テーブル。新たな収集はしない）

| 材料 | 範囲 | 目的 |
|---|---|---|
| 一行日記（`memory_chunks` source_type=日記） | 直近14日 | 本人の状態・引っかかり |
| 週報（`weekly_reports`） | 直近4週 | 営業の事実ログ。団体別の動き |
| 会議（`memory_chunks` source_type=会議） | 直近14日 | 相手の反応・懸念 |
| 健康（`health_metrics` 日次サマリ） | 直近28日 | 体調と仕事の連動を見るため |
| ToDo（`daily_actions` / `strategic_todos`） | 未完のもの | 詰まっている場所 |
| 振り返り（`retrospectives`） | 直近2件 | 本人が既に自覚していることを重複して言わないため |
| **過去の示唆（`insights`）** | 直近30日 | **同じことを繰り返さない／解決したかを見る** |

最後の1行が肝である。過去の示唆を読むからこそ、
「先週から同じことを言い続けている」「前に言ったあれは解決した」を**AI自身が翌晩に判定できる**。
これが (c) の欠損を埋める本体になる。

### 出すもの（1晩あたり 3〜5件）

| 種別 | 中身 | 必須 |
|---|---|---|
| `改善` | 本人の動き方への示唆。目標(1) | — |
| `横断` | 領域をまたいだ気づき。健康×営業、日記×会議など | — |
| `異議` | **吉井さんの現在の判断・進め方に対する反対の筋** | **毎晩必ず1件** |
| `問い` | 材料からは判断できず、本人に聞かないと進まないこと | — |
| `継続` | 過去の示唆で未解決のもの（再掲。新規カウントに含めない） | — |

**`異議` を必須枠にする理由。** 総点検で全システムプロンプトを通読したところ、
**吉井さんの判断に異議を唱えろと指示している箇所は1つも無かった**。
全ルートが「与えられた資料の事実のみに基づけ」「憶測で創作するな」と縛られており、
精度としては正しいが、反対意見や別の筋を出す余地を構造的に封じている。
オブジェクションは `weapons` の想定問答で代替されているが、あれは「顧客→提案」の向きであって
「AI→吉井さん」ではない。枠を切らないと、モデルは安全側に寄って当たり障りのないことを言う。

## 3. どう動かすか

### 実行場所: Mac の launchd（Vercel cron ではない）

| | Vercel cron | **launchd（採用）** |
|---|---|---|
| 実行時間 | Hobby は `maxDuration = 60` 秒 | 制限なし |
| 実績 | LLMを呼ぶジョブの実績なし | 進捗エージェント（22:30）ほか13本が稼働中 |
| 心拍監視 | — | `job_heartbeats` の仕組みが既にある |

60秒の壁は既に実害を出している。`procedure-refine` には
「thinking有りで56秒、外しても62.6秒かかった」という実測コメントが残り、
`thinking:false` を明示している箇所がリポジトリに7つある。
**領域横断で数千字を読んで考える処理を60秒に収めるのは無理で、収めようとすると思考の質が落ちる。**
既に実績のある launchd 側で回す。

- ジョブ名: `yakan-sanbo`
- 時刻: **23:00**（進捗エージェント 22:30 の後。その日の作業ログが出揃ってから読む）
- 心拍: 実行のたび `job_heartbeats` に打刻。`WATCHED_JOBS` へ `staleHours: 48` で追加する
  （Macを閉じている間は走らないため、既存の毎日ジョブと同じ48時間に合わせる）
- 実装: 既存ジョブと同じ形。Next.js の API ルート `/api/night-advisor`（POST・`CRON_SECRET` 照合）を
  launchd から叩く。**Vercel ではなくローカルの Next.js を叩くか、ロジックをスクリプト側に置くかは実装時に決める**
  （Vercel 経由だと結局60秒の壁に当たるため、**ローカル実行が前提**）

### 使うモデルと思考設定

- `lib/llm.ts` の `structured()` を通す（`new Anthropic()` の直書き禁止は既存規律）
- モデルは `DEFAULT_MODEL`（現 `claude-sonnet-5`）のまま。環境変数 `AIWORKOS_MODEL` で一括切替できる既存の仕組みに乗る
- `thinking: {type:"adaptive"}`。**60秒制限が無いので `thinking:false` にしない**——ここが launchd を選ぶ最大の意味

## 4. 保存するもの

### 新テーブル `insights`

```sql
create table public.insights (
  id            uuid primary key default gen_random_uuid(),
  generated_on  date not null,                    -- どの晩の分か（JST）
  kind          text not null,                    -- 改善 / 横断 / 異議 / 問い / 継続
  title         text not null,                    -- 一行。何が起きていそうか
  body          text not null,                    -- 本文。なぜそう言えるか
  evidence      jsonb not null default '[]',      -- 根拠。{source_type, title, event_date, chunk_id?} の配列
  related_orgs  text[] not null default '{}',     -- 関係する団体（あれば）
  -- 継続の追跡。前の晩の示唆を引き継いだ場合にその id を指す
  continues_id  uuid references public.insights(id),
  -- 人の判断。ここが自己改善の燃料になる
  verdict       text,                             -- adopted / deferred / off_target / null(未判断)
  verdict_at    timestamptz,
  verdict_note  text,                             -- 「なぜ的外れか」を書ける。次の晩が読む
  -- 結果の追跡（Phase 3 で使う）
  outcome       text,                             -- resolved / faded / null
  outcome_at    timestamptz,
  model         text,
  created_at    timestamptz not null default now()
);
```

**`verdict_note` を置く理由。** 「的外れ」とだけ記録しても次の晩は同じ間違いを繰り返す。
理由が1行あれば、翌晩のプロンプトに「前回これは的外れと言われた。理由はこれ」として差し込める。
ここが、示唆を出しっぱなしにしないための最小の仕掛けになる。

**`evidence` を必須にする理由。** 根拠の無い示唆は検証できず、検証できないものは信用されない。
既存の全ルートが「資料の事実のみ」で縛られているのと同じ規律を、仮説層にも別の形で効かせる
——断定は許すが、**どの材料から言っているかは必ず示させる**。

### 画面: ホームの参謀カード

既存の「今朝の気づき」の下に「今朝の示唆」として並べる。**上下で明確に分ける。**

- 上（既存・事実）: 「日記が3日空いています」
- 下（新規・仮説）: 「【仮説】○○市の動きが2週間止まっています。会議録では△△の懸念が
  未解決のまま残っており、ここが詰まっている可能性があります」＋根拠2〜3件

各示唆に **採用 / 見送り / 的外れ** の3ボタンを置き、押すと `verdict` に記録する。
`的外れ` を押したときだけ理由の入力欄を出す（他は1クリックで終わらせる。摩擦を増やすと押されなくなる）。

## 5. やらないこと（この段階では）

意図的に外す。合意を取りやすくし、失敗したときに戻しやすくするため。

- **自動での実行・修正はしない。** 示唆を出すだけ。何も直さず、何も消さず、誰にも送らない
- **tool use は入れない。** 材料は固定のSQLで集める。ツール化は Phase 2 の提案エージェントで先に試す
- **Push通知には出さない。** 朝のPush（`/api/cron/daily-todo`）は現状ルールベースの事実のみで、
  仮説が混ざると通知の信用が落ちる。まず画面だけで運用し、精度を見てから判断する
- **既存の参謀・検知器は一切触らない。** 追加のみ
- **記憶層（`memory_chunks`）には書き戻さない。** 示唆は `insights` に閉じる。
  書き戻すと検索結果にAIの仮説が混ざり、次のAIがそれを事実として引く危険がある
  （これは Memory 2.0 の「書き込みは store-memory の一本関所」という規律とも整合する）

## 6. 成否の見方

「動いたから完成にしない。変わるべきものが変わったかを実データで示してから完了と言う」
（`docs/memory-2-history.md` §9）に従い、**運用2週間後に次を実測して判断する**。

| 指標 | 見たいこと | 危険な値 |
|---|---|---|
| 判断がついた割合 | 示唆が読まれているか | 5割を切る＝読まれていない。出す件数か出し方が悪い |
| `adopted` の割合 | 当たっているか | 1割未満＝的外れが多すぎる。材料かプロンプトを見直す |
| `off_target` の割合 | 外し方の傾向 | 3割超＝プロンプトを `verdict_note` から書き直す |
| `継続` の再掲回数 | 同じ話を繰り返していないか | 同一 `continues_id` が5回超＝人が動けない話を言い続けている。出し方を変える |
| 実行時間 | launchd 側の余裕 | 10分超＝材料を絞る |

**2週間で `adopted` が1件も出なければ、この方式は畳んで別の形を考える。**
作ったものを残すことが目的ではない。

## 7. 実装の順序

1. `insights` テーブルを作る（`supabase/migrations/` に追加。production-change-protocol に従う）
2. 材料を集める関数を書く（`lib/nightAdvisor/collect.ts`）。**まずLLM抜きで、集まった材料を目視確認する**
3. プロンプトと `structured()` の呼び出しを書く（`lib/nightAdvisor/think.ts`）。手動実行で3晩ぶん試す
4. 3晩ぶんの出力を吉井さんと一緒に読み、**出す/出さないの線を決めてからDB保存を有効にする**
5. ホームの参謀カードに表示と3ボタンを足す
6. launchd に `yakan-sanbo` を登録し、`WATCHED_JOBS` へ追加する

**4 の関門を飛ばさない。** いきなり毎晩保存を始めると、質の悪い示唆が溜まって
`insights` そのものが信用されなくなり、後から立て直せなくなる。

## 8. この設計が埋めない欠損

正直に書いておく。夜間参謀を入れても、次は埋まらない。

- **(b) 自分で探す手** — 材料は固定SQLの決め打ちのまま。AIが「もっと見たい」と言えない
- **打ち手の成否** — `verdict` は「示唆が良いと思ったか」であって「実際に効いたか」ではない。
  打ち手→実行→結果を結ぶテーブルは依然として無い（Phase 3）
- **検索品質の頭打ち** — `lib/chunker.ts` と `documents` テーブルが死蔵のままなので、
  「切り方を変えて再生成する」切り札は使えないまま（Phase 2）

## 9. 実装で分かったこと・設計から変えた点（2026-09-12）

設計どおりに作れなかった／作ってみて初めて分かった箇所を残す。
次に触る人が「なぜこうなっているか」を辿れるようにするため。

### 9-1. ローカルの Next を自分で起こす必要があった（設計になかった）

設計 §3 で「launchd からローカルの Next.js を叩く」と書いたが、
**吉井さんが常時 `npm run dev` を上げている保証が無い**ことを実装時に見落としていた。
他の定期ジョブ（`notion-sync.sh` 等）を読むと、すべて Vercel 本番URLを叩いている。
夜間参謀だけはそれができない（実測117〜211秒。関数タイムアウトに当たる）。

そこで `~/.local/bin/yakan-sanbo.sh` が次をやる:
- 3020 が既に応答していれば**それを使い、絶対に止めない**
  （作業中のサーバーを夜中に殺すと、翌朝「勝手に落ちた」ことになる）
- 応答が無ければ自分で起こし、**自分が起こしたぶんだけ**終了時に止める

実測: 起動2秒、生成198秒、後片付けまで自動。両経路ともテスト済み。

### 9-2. 材料の切り方に向きのバグがあった

会議録は総量20,000字で切っているが、**古い順に詰めていたため上限に当たると新しい会議から落ちていた**。
直近ほど重い材料なのに、重いものから捨てる作りだった。しかも件数は合うので画面からは気づけない。
実測で会議は14日ぶんで170チャンクあり、上限は確実に効く。
→ `clip()` を「新しい順に詰めて、読ませるときは時系列に戻す」に直した。

### 9-3. 根拠のタイトルが空になることがあった

ToDo 由来の根拠が `{source_type:"ToDo", title:"", event_date:""}` になり、
**何を見て言ったのか確かめられない示唆**が出た（設計で「根拠が空の示唆は出させない」と
書いていたが、配列が空でないだけでは足りなかった）。
→ スキーマの description で「title を空にしてはいけない／見出しが無い材料は中身そのものを書く」
と明示し、プロンプト側にも同じ指示を置いた。再実行で根拠13件すべてにタイトルが入ることを確認。

### 9-4. 過去の晩を再現するとき、未来のデータが混ざっていた

`mode:dry` に `today` を渡して過去の晩を再現できるようにしたが、
材料の取得に上限日を掛けていなかったため、**その晩には存在しなかった記録まで読んでいた**。
後から見れば当たっているように見えるだけの示唆が出て、出来の比較にならない。
→ 日記・会議・週報・振り返り・過去の示唆すべてに `lte.today` を掛けた。
ToDo だけは消し込みの履歴を持っていないため現在の状態しか取れない（その旨コメントに明記）。

### 9-5. 無人実行のための再試行を足した

試行中、4回成功したあと5回目が `Connection error.` で落ちた（2分前後の生成なので途中で切れうる）。
無人で毎晩走るジョブでこれが起きると、翌朝カードが空になるだけで、
気づけるのは心拍が48時間途絶えたときになる。
→ 一時的失敗（HTTPの429/5xx、および接続断）に限り、30秒待って**1回だけ**やり直す。
2回に増やさないのは、残高切れやキー無効のような「待っても直らない」失敗を引き延ばさないため。

なお `lib/llm.ts` の `isTransientError` はHTTPステータスを見るので、
ステータスの付かない接続断は拾えない。`think.ts` 側に `isConnectionError` を置いた。

### 9-6. maxTokens を 16,000 → 24,000 に上げた

実測の出力は8,500〜12,400トークン（思考込み）。16,000では余裕が薄く、
足りないと途中で切れて2分ぶんの生成が丸ごと無駄になる。

### 9-7. 心拍は二重に打つ

`with-heartbeat.sh`（ラッパー）と API ルートの両方が `yakan-sanbo` の成功を打つ。
重複するが害は無く、それぞれ別の価値がある:
- ラッパー … 失敗も打つ。ネットワーク断のときはローカルにスプールして次回送る
- ルート … 手動実行（launchd を通さない実行）でも心拍が新しくなる

### 9-8. 初日の実績

2026-09-12 の晩に本番保存を実施。示唆4件（改善・横断・異議・問い が1件ずつ）、
根拠は合計16件でいずれもタイトル入り。異議枠は3晩すべてで機能した。

**評価は運用2週間後に §6 の指標で行う。動いたことを完成としない。**
