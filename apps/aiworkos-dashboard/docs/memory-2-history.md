## 1. Memory 2.0 開始時点

### 当初の問題意識
`/status` の「記憶の健康診断」が、正常なデータを二重登録と誤認していた。調べていくと、根本は**「chunk（断片）」と「document（文書）」を区別する手段が無い**ことだった。

### 当時の `memory_chunks` の構造
```
id uuid / source_type text / source_id text / organization text / title text
content text / event_date date / metadata jsonb / embedding vector(384) / created_at
```
開始時 **1,458行**（クローズ時 1,459行。差の1行は8/28 23:12にPLAUD議事録同期が登録した広島市議会の議員レク）。

### `source_id` の意味
行の識別子。**1,458件すべて一意**（重複ゼロ）。ただし書式が経路ごとにバラバラだった。

| 形 | 例 |
|---|---|
| PLAUD録音 | 裸の32桁hex、または `plaud:<hex>` |
| Notion | `https://app.notion.com/p/<hex32>` |
| 会議 | `meeting:<名前><日付>:N` |
| 成果物 | `deliverable:<団体>:<ファイル名>:<位置>` |
| 内部生成 | `weekly_report:<uuid>` `retrospective:` `refine:` `slide-refine:` `procedure-refine:` |
| カタログ | `qa:` `weapon:` `gakkai:` `metrics:` |
| 月次報告 | 裸のUUID（当時。のち `monthly_briefing:<uuid>` へ統一） |

### 構造上いちばん大事だった事実
**`chunk_index` 列が存在しなかった。** 「何番目のチャンクか」は title末尾・`metadata.位置`・`source_id`末尾に、経路ごとに違う書式で入っていた。

実データにあった title の接尾辞：`｜1/16`(18件) `｜text1`(119件) `｜p1`(19件) `｜p10-1`(39件) **`｜1`（裸の数字・621件）**、さらに多段（`…｜報告書｜slide1｜1`）。

### なぜ canonical / source_document という2階層を導入したか
1つのIDでは足りなかった。**同じ録音から別々に生成された「別版」が実在した**ため。

- `plaud:36dba3aa…` 北九州市／同題・212字 vs 232字
- `plaud:8da2d2ce…` 横浜市／同題・231字 vs 185字
- `plaud:b08f952e…` **豊島区203字・豊島区204字・新宿区208字**（題も団体も違う3行目）

3文書7行、いずれも content の md5 が全部違う＝同じ行が2回入ったのではなく**別版**。そこで、

| 列 | 意味 |
|---|---|
| `canonical_document_id` | **実体**。同じ録音・同じNotionページから生まれたものは同一 |
| `source_document_id` | **取込文書＝版**。1回の取り込みで入った1つの文書 |
| `chunk_index` | 版の中の0起点の位置 |
| `ingest_scheme` | どの規則で同一性を決めたか（7分類） |

**`variant_id` 列は不要と判断した。** `source_id` が全件一意なので `(canonical_document_id, source_id)` が既に版の一意鍵として機能する。

### 同一性に**使わない**と決めたもの
`title` / `event_date` / `organization` は `deriveIdentity` の**引数に取らない**。

- 団体名を鍵に入れると、団体名を直しただけで別物になる（第4.1弾で実害を確認）
- `title` は第7.2弾の実測で「有無による結果差 **0/1458**」だったので引数から外した
- 使わないことを規約ではなく**関数の形**で保証する

### 第6〜6.1弾：Shadow Mode（`ff783a0`）

### 第7.0〜7.2弾：writer棚卸しとIdentity純粋関数（`8fe36d9` `f236304`）
- **書き込み口は `store-memory` Edge Function ただ1つ**（`memory_chunks` はRLS有効・ポリシー0）

- **`_shared/` に置く理由**：Deno（Edge）とNode（アプリ・テスト）の両方から同じ1本を読む。二重実装にすると片方だけ直したとき既存データと新規データで別の同一性が生まれる

### 第7.3〜7.4弾：Dual Write（`2b1f265`・本番 store-memory v4）
`store-memory` を**同一性を決める唯一の関所**にした。

| 規則 | 挙動 |
|---|---|
| caller が canonical等を送る | **400** で拒否（`CALLER_FORBIDDEN_KEYS`） |
| 未知の `source_id` 書式 | **422**。null のまま成功にしない（未知のwriterに気づけなくなるため） |
| deliverable で `chunk_index` が無い | **422**。0を入れて成功させない（1文書の全chunkが0番になり衝突する） |
| INSERT / UPDATE | **両方**に4列を書く（UPDATEに入れ忘れると入れ直しのたび古い同一性が残る） |

**caller から受け取るのは deliverable の `chunk_index` ただ1つ。** 位置の札（`text1` `p2-1`）は順番がその行だけでは決まらず、兄弟行を数える方式は同時挿入で競合するため。

番号の優先順：①source_idの`#N` ②metadata.位置の`i/n`の分子 ③source_id末尾の`:N` ④callerの値 ⑤どれも無ければ**0に固定**（通し番号で埋めない。別版どうしが 0,1 と並んで衝突が消えて見えるため）。

### 第7.5弾：Guardian（監視）（`39a3489`）

## 3. やらないと決めたこと（最重要）

**ここに書いてある案を再提案しないこと。** すべて本番データで検証したうえで却下している。

### 3-1. `canonical_document_id` は「現実世界の出来事」ではない
canonical は**「同じ録音・同じNotionページから生まれたか」**を表すだけ。同じ商談について別々の録音が2本あれば、canonical は2つになる。逆に1本の録音から別団体向けの要約を2つ作れば、**別団体なのに canonical は1つ**になる。

実例 `plaud:b08f952edde1234412b51c23b51af665`：
```
chunk 3件 / 取込文書 3件 / 団体 = 豊島区・新宿区
  [豊島区] 7/23商談の最終戦略（議員同席交渉）        sim=0.9526
  [豊島区] 7/23商談の最終戦略（議員同席交渉）        sim=0.9481
  [新宿区] 新宿区との面談戦略（7/23課長合意獲得プラン） sim=0.9332
```
**「1つの出来事＝1つのcanonical」だと思って設計すると壊れる。**

### 3-2. RAGで canonical dedup を使わない
上の実体を canonical で畳むと**1件に潰れ、新宿区の文書（sim 0.9332）が丸ごと落ちる**。低品質な重複ではなく、別団体の別文書。畳むなら `source_document_id` のほうが安全（3件とも残り、両団体が残る）。

### 3-3. source_document dedup も本番採用しない（**一度推奨し、実データを見て撤回した**）
第7.9弾では「source_document 単位が推奨」と結論した。フィルタなしの評価では、文書数が増え・token が減り・relevance の低下は −0.001〜−0.015 と小さかったため。

**第8.0弾でフィルタ付きを調べて撤回した。**

```
団体で絞ると、成果物はほとんどが1文書しかない
  豊島区 48chunk → 1文書      八王子市 26 → 1
  新宿区 23 → 1               練馬区 17 → 1
  ソフトバンク 17 → 1          北九州市 27 → 4
  共通 331 → 76
```
1つの大きな提案書がその団体の資料の**すべて**なので、畳んだ瞬間に文脈が消える。

| caller | chunk方式 | document方式 | 文脈 |
|---|---|---|---|
| agent 成果物 豊島区 | 40 chunk / 12,642字 | 1 / 374 | **3%** |
| agent 成果物 八王子市 | 26 / 10,282 | 1 / 282 | **3%** |
| agent 成果物 新宿区 | 23 / 8,947 | 1 / 400 | **4%** |
| refine 団体別 北九州市 | 20 / 5,924 | 4 / 1,315 | **22%** |
| agent 共通資料 豊島区 | 20 / 5,418 | 20 / 6,000 | 111% |
| refine 成果物(横断) 自治体 | 20 / 7,032 | 20 / 6,599 | 94% |

**32 caller のうち18で文脈が6割未満に激減。** 合計 202,101字 → 78,339字（**39%**）。

境界は明確：**団体で絞る（文書1〜4件）→ 破壊的／共通資料・分類横断（文書が多い）→ 有効**。

### 3-4. candidate を増やしても直らない（oversampling不足ではない）
文書自体が存在しないため。全本番データの分布：

| 種別 | 団体×種別の組 | 文書が1つだけ | 20文書未満 | 最大文書数 |
|---|---|---|---|---|
| 成果物 | 16 | **11** | 15 | 76（共通のみ） |
| 会議 | 31 | **18** | **31（全部）** | 14 |
| 週報 | 52 | **38** | **52（全部）** | 5 |

**`document_limit=20` を満たせる団体別の組み合わせは、成果物の「共通」ただ1つ。** 動的oversampling も iterative retrieval も効果がない。**実装するだけ無駄。**

### 3-5. v3 は dedup ではなく「多様性優先の並べ替え」を候補にした
chunk予算はそのままに、各文書の最良chunkを先に並べ、埋まらなければ2番目・3番目と周回する。

| 方式 | chunk計 | 文書計 | 文字計 |
|---|---|---|---|
| ①chunk（現状） | 606 | 151 | 202,101（100%） |
| ②document畳み | 259 | 259 | 78,339（**39%**） |
| ③**多様性優先** | **606** | **259** | **203,218（101%）** |

**③は「②の多様性」を「①の文脈量」のまま実現する。** しかも文書が1つしかない caller では自動的に①と同じ結果に退化するので starvation しない。**未実装。**

③を入れるときの注意：**並び順が変わる＝AIの出力が変わりうる**。第7.8弾までの「結果が1件も変わらない」とは質の違う変更なので、Golden は差分が出る前提の検証設計が要る。**第8.1弾のキャッシュ署名修正は、この前提条件として先に行った。**

### 3-6. `candidate_chunk_limit = 100` の根拠
- **品質**：候補80で 8/8テーマが基準（200）と完全一致。40では `定額小為替`（重複率65%）が不足。100は2割の余裕
- **latency**：候補40比で最大 +1.3ms。**絞り込み検索では候補を使い切るので増加ゼロ**

| フィルタ | cand=40 | 80 | **100** | 120 | 200 |
|---|---|---|---|---|---|
| なし | 0.97 | 1.65 | **2.09** | 2.44 | 3.92 |
| source_typeのみ | 1.22 | 2.14 | **2.52** | 2.96 | 4.77 |
| organizationのみ | 3.66 | 5.22 | **5.17** | 5.16 | 5.12 |
| 両方 | 4.77 | 4.76 | **4.78** | 4.71 | 4.71 |

（p50・ミリ秒・サーバ側）

### 3-7. Event / Entity Layer を Memory 2.0 に入れなかった理由
Memory 2.0 の目的は「**同一性の土台を作る**」ことに限定した。Event / Entity は canonical の**上**に載る概念で、土台が揺れている状態で載せると、両方が同時に壊れたとき原因を切り分けられない。3-1のとおり canonical は現実世界の出来事と1対1ではないので、Event Layer を作るなら**別の対応表が要る**。土台が固まった今なら着手できる。

### 3-8. Identity 4列の下流公開を第7.8弾で見送った理由（A案採用）
B案（13列をそのまま返す）で壊れる caller は**調査では見つからなかった**（zod等の厳密な検証なし、型は構造的で余分なキーを無視、行をまるごとJSON化してプロンプトに入れる箇所なし、キャッシュ署名は件数と本文長しか見ない）。**33ケース・497行のShadow比較でも挙動差0**、応答サイズ +6.2%。

それでもA案にしたのは、**何か起きたときに「読む先を変えたせい」か「列を増やしたせい」かを切り分けるため**。`/search` は応答をそのままブラウザへ素通ししているので、B案はAPI契約の変更そのものになる。

**安全と分かっているので、次フェーズで公開してよい。** 入口は `search-memory` の `V1_COMPAT_COLUMNS` に足すだけ。

## 4. 発見した障害・バグ

### 4-1. PostgREST の1000行上限で監査が黙って切れる
`lib/advisor/client.ts` の `getRows` は**ページングしない**。`memory_chunks` は1458行あるので上限で切られ、切られたまま数えると「異常なし」と嘘をつく。検知器は自前で Range ヘッダを送る。

### 4-2. title接尾辞による document count 不整合
`stripChunkSuffix` が `｜1/16` 形式しか落としておらず、`｜text1` `｜p10-1` `｜1`（裸の数字621件）が残っていた。**接尾辞は積み重なる**（`…｜報告書｜slide1｜1`）ので、既知の形が無くなるまで繰り返す。ただし**広く消さない**——`｜全体` `｜報告書` のようなチャンク番号でない末尾は残す（消しすぎると別文書を取り違えて潰す）。

### 4-3. `org-history` の集計問題（二重実装）
同じ規則が2箇所にあり、片方だけ育った。

```
org-history : /｜\d+\/\d+$/ を1回だけ
アプリ側     : ｜n/m ｜textN ｜slideN ｜imgN ｜pN ｜N を最大5回
```
**本番の会議287行に `｜n/m` は0行。** 2026-08-26に入れた修正は実データを1行も剥がしていなかった。札幌市が「会議6件」（実際2件）、アグレックス3件（実際1件）、横浜市11件（実際7件）。

→ `_shared/chunkTitle.mjs` に1本化（`29006fa`）。

**教訓：直したつもりの修正は、実データで剥がせた行数を数えて確かめる。**

### 4-4. `/status` の count 問題
`dashboard_stats()` の `org_status[].meetings` が `count(*)` のまま取り残されていた。18団体でズレ（八王子市27→2、新宿区26→4、墨田区21→2、事業者対策19→1、練馬区15→1）。

→ `count(distinct canonical_document_id)` へ（`040e738`）。SQLに接尾辞の正規表現を書き写すと**3つ目の実装**になるので、列で数える方を選んだ。

### 4-5. HNSW filter starvation（**いちばん実害が大きかった**）
`memory_chunks_embedding_idx` は **hnsw**（近似検索）で `hnsw.ef_search=40` / `iterative_scan=off`。**候補40件を先に取ってから絞り込む**ため、`source_type` や `organization` で絞ると要求件数に遠く届かない。

| | 適用前 | 適用後 |
|---|---|---|
| 取りこぼしている組（実在5行以上の団体×種別 31組） | **25 / 31** | **0 / 31** |
| 充足率 | **54%** | **100%** |
| 新宿区×成果物（実在23行・要求20） | 3件 | 20件 |
| 豊島区×会議（実在10行・要求20） | 3件 | 10件 |

`match_count=5` ですらフィルタ付きだと 2/6 しか満たせず、`match_count=50` は40件で頭打ちだった（agent の 40 は事実上の上限で無意味だった）。

**並び順そのものは壊れていなかった。** 索引なしの exact search と突き合わせた60条件すべてで、返ってきた行は exact の**上位prefixと完全一致**。「順序は正しいが途中で打ち切られる」状態だったので、直しても既存の並びは崩れない。

### 4-6. `iterative_scan = strict_order` を採用した理由
ef_search を上げる案と recall は同じ（どちらも100%）だが、**latency の性質が正反対**。

| 方式 | フィルタなし p50 | 両方フィルタ p50 |
|---|---|---|
| 現状 ef40/off | 0.8ms（recall100%） | 0.5ms（**recall34%**） |
| ef120/off | **10.8ms** | 0.9ms（100%） |
| **strict_order** | **0.9ms** | 5.0ms（100%） |

ef を上げると**壊れていないフィルタなし検索（/search の既定経路）が13倍**になる。iterative_scan は候補が足りないときだけ探索を継続するので、足りている検索は無料。`relaxed_order` でなく `strict_order` にしたのは並び順の厳密性を保証させるため。

**グローバル設定にしない。** `ALTER DATABASE`/`ALTER ROLE` だと今後足すどの vector 検索にも一律に効く。**関数の SET 句なら RPC 2本の中だけ**で、関数を出れば元の値に戻る。

**★罠：先に vector を読ませないと権限エラーになる**
```
ERROR: 42501: permission denied to set parameter "hnsw.ef_search"
```
拡張のGUCが未ロードのセッションでは仮置き扱いになり、非スーパーユーザーは `ALTER FUNCTION ... SET` できない。**ALTER の前に `SELECT ('[1,0]'::vector <=> '[0,1]'::vector);` を1回流す。**

### 4-7. RAGキャッシュ署名の衝突
旧署名は `${件数}:${最新日}:${content長の合計}` だけ。**和は順序に依らない**ので、中身や並びが変わっても署名が一致し、古いAI回答が返り続ける。

実害の経路2つ（どちらも本番データで再現）：
1. **並び順が変わっても署名が同じ**。`agent 成果物 北九州市`（成果物4文書）で、集合は同じ・順序だけ違うのに署名が完全一致
2. **同文字数の誤字修正を検知できない**。`transcription_dictionary` 140語のうち**40語が同じ文字数の置換**（`精霊市→政令市` `政令士→政令市` `富士フィルム→富士フイルム` `東洋資料→東洋紙業` `有勝化→有償化` `法人成長オンラインサービス→法人請求オンラインサービス` ほか）。`transcription-typo-fix` で直しても `content.length` が動かず、誤字入りの提案が残り続ける

### 4-8. TTLが存在しない
`proposal_cache` に期限の列も判定コードも無く、`proposal-cache` Edge Function にも期限ロジックが無い。**署名が変わらない限り永久にキャッシュが返る**（最長42日経過していた）。だから署名の正しさが唯一の防波堤になる。

### 4-9. 月報側はさらに深刻
`weekly_reports` に **`updated_at` 列が存在しない**。既存の週報を書き直しても `created_at` は動かないので、**本文ハッシュ以外に検知手段が無い**。旧署名は文字数合計しか見ておらず、同じ文字数の書き直しを永久に取りこぼしていた。

### 4-10. テストの `check()` 自体が空振りしていた
このプロジェクトの `check(label, 真偽値, 補足)` に対して `(実際, 期待)` の形で呼び、**新規5件が常に成功する空振り**になっていた（第7.8弾）。`check("...", res.status, 200)` は `200` が truthy なので必ず通る。

→ 以降は**わざと壊して本当に落ちるか**を確認するようにした（第8.1弾で実施：本文hashを外す→4件失敗、順序を無視→3件失敗、v1に戻す→4件失敗）。

### 4-11. backup失敗時の exit code を一度誤認した
第7.4弾で「バックアップ失敗時の終了コードが0だった」と報告したが、**誤り**。`~/aiworkos-backups/backup.sh` は元から失敗時に `exit 1` を返し、`with-heartbeat.sh` も `rc` を保持して `job_heartbeats` に `kind: fail` を打刻し `exit "$rc"` で返していた。**チェーン全体が最初から正しかった。**

0に見えたのは `backup.sh | tail -3` とパイプして **`tail` の終了コード**を見ていたため。同じ罠を同一セッション内で2度踏んだ。

**終了コードを確認するときパイプしない。`> log; echo $?` にする。**

## 9. 本番を触るときの型（この2日間で確立した品質基準）

**実データ確認 → Shadow → テスト → 本番 → Golden → rollback確認**

1. **実データ確認**：READ ONLYで本番を数える。推測で設計しない
2. **Shadow**：新方式を並走させ、旧と同じ入力で突き合わせる。旧は消さない
3. **テスト**：純粋ロジックに切り出して固定する。**わざと壊して本当に落ちるか確かめる**
4. **本番**：変更は1つずつ。「読む先を変える」と「列を増やす」を同時にやらない
5. **Golden**：変更前に実経路で結果を保存し、変更後に同じ入力で突合。許容差は原則0。差が出たら原因調査より先にrollback候補として扱う
6. **rollback確認**：戻し方を先に書いてから適用する。DBを触らずに戻せる形を優先する

**「動いたから完成」にしない。変わるべきものが変わったかを実データで示してから完了と言う。**
